## 2. พจนานุกรมค่าคงที่ (Single Source of Truth — ห้ามนิยามซ้ำที่อื่น)

ค่าเหล่านี้ต้องถูกประกาศ **ที่เดียว** ในแต่ละฝั่ง แล้ว import ไปใช้ ห้าม hardcode กระจาย

### 2.1 เพศ `mb_gender`
`1` = ชาย · `2` = หญิง

### 2.2 เป้าหมาย `mbs_target`
`1` = ลดน้ำหนัก · `2` = เพิ่มกล้ามเนื้อ · `3` = รักษาน้ำหนัก

### 2.3 เกณฑ์สีโภชนาการ `fd_traffic_light` (3 สี)
| ค่า | สี | Hex | ความหมาย |
|---|---|---|---|
| `1` | เขียว | `#10B981` | กินได้ปกติ |
| `2` | เหลือง | `#F59E0B` | กินได้แต่ควบคุมปริมาณ |
| `3` | แดง | `#EF4444` | ควรจำกัด |

**ต้อง `NOT NULL DEFAULT 2`** — ห้ามปล่อยเป็น NULL เด็ดขาด เพราะหน้าจอจะแสดงสีไม่ได้

### 2.4 เกณฑ์ BMI `mbh_eval_result` (4 ระดับ — คนละชุดกับสีอาหาร!)
| ค่า | ผลประเมิน | ช่วง BMI | Hex |
|---|---|---|---|
| `1` | ผอม | `BMI < 18.5` | `#3B82F6` น้ำเงิน |
| `2` | ปกติ | `18.5 ≤ BMI < 23.0` | `#10B981` เขียว |
| `3` | ท้วม | `23.0 ≤ BMI < 25.0` | `#F97316` ส้ม |
| `4` | อ้วน | `BMI ≥ 25.0` | `#EF4444` แดง |

**ขอบเขตต้องใช้ `<` ฝั่งบนเสมอ ห้ามใช้ `<= 22.9` / `<= 24.9`** เพราะจะเกิดช่องโหว่ที่ค่า 22.95 และ 24.95 ตกหล่นไม่เข้าช่วงไหนเลย (บั๊กนี้มีอยู่จริงใน `bmiToGaugeAngle()`)

> **ต้องแยกโทเคนสี BMI ออกจากสีอาหารให้ชัด** ปัจจุบัน "ท้วม" กับ "เหลือง" ใช้ `#F59E0B` เหมือนกัน ทำให้อ่านผิดความหมาย ให้ "ท้วม" เปลี่ยนเป็น `--color-orange: #F97316` และตั้งชื่อตัวแปร CSS แยกกันเป็น `--bmi-*` กับ `--food-*`

### 2.5 มื้ออาหาร `dfd_meal_type`
`1` = เช้า · `2` = กลางวัน · `3` = เย็น · `4` = ว่าง

### 2.6 การนอน — ต้องแยก 2 ค่าให้ขาดจากกัน
`dslp_eval_result` (**ระบบคำนวณเอง** จากจำนวนชั่วโมง — ผู้ใช้แก้ไม่ได้)
`1` = น้อยเกินไป (`< 7 ชม.`) · `2` = พอดี (`7 ≤ h ≤ 9`) · `3` = มากเกินไป (`> 9 ชม.`)

`dslp_quality_score` (**ผู้ใช้เลือกเอง** ตอนบันทึก — ระบบห้ามคำนวณให้)
`1` = แย่ · `2` = ปานกลาง · `3` = ดี

> ปัจจุบัน 2 ค่านี้ถูก derive จากชั่วโมงเหมือนกันทั้งคู่ ทำให้ซ้ำซ้อนและขัดแย้งกันบนหน้าจอ ต้องแก้

### 2.7 ตัวคูณระดับกิจกรรม `mbs_activity_level`
เป็น **ตัวคูณ TDEE** ไม่ใช่ "ความถี่ต่อสัปดาห์" (คอมเมนต์ใน `Datasic.sql` เขียนผิด ต้องแก้)
`1.20` นั่งทำงาน · `1.375` เบา · `1.55` ปานกลาง · `1.725` หนัก · `1.90` หนักมาก

## 3. สูตรคำนวณ (ต้องอยู่ในไฟล์เดียวฝั่ง Go เท่านั้น)

```
อายุ  = คำนวณจาก mb_birth_date เทียบกับ "วันที่คำนวณ" (mbh_record_date)
        ต้องหักปีที่ยังไม่ถึงวันเกิด — ห้าม hardcode และห้ามใช้ (ปีปัจจุบัน - ปีเกิด) เฉยๆ

BMI   = น้ำหนัก(กก.) / (ส่วนสูง(ม.))²        ปัดทศนิยม 2 ตำแหน่ง

BMR   (Mifflin-St Jeor)
      ชาย  = (10 × น้ำหนัก) + (6.25 × ส่วนสูง ซม.) − (5 × อายุ) + 5
      หญิง = (10 × น้ำหนัก) + (6.25 × ส่วนสูง ซม.) − (5 × อายุ) − 161

TDEE  = BMR × mbs_activity_level

TDEE_TARGET ตาม mbs_target
      1 ลดน้ำหนัก      = TDEE × 0.85
      2 เพิ่มกล้ามเนื้อ = TDEE × 1.15
      3 รักษาน้ำหนัก    = TDEE × 1.00
```

**หลักฐานบั๊กที่ต้องแก้:** แถว `mbh_id=2` ในฐานข้อมูลปัจจุบันเก็บ BMR = 1610.00 แต่ค่าที่ถูกต้องคือ 1645.00 ส่วนต่าง 35 = 5 × 7 ปี → ตอนนั้นคำนวณอายุเป็น 28 ทั้งที่สมาชิก `mb_id=3` เกิด 2004-10-25 ณ วันที่ 2026-08-10 มีอายุ 21 ปี **ให้เขียน unit test ครอบเคสอายุโดยเฉพาะ**

**เคสที่ยังไม่เคยถูกทดสอบเลย:** ในฐานข้อมูลปัจจุบันมีแถว `member_bmr_history` แค่ target 2 กับ 3 — **ไม่มี target = 1 (ลดน้ำหนัก) สักแถวเดียว** ต้องทดสอบเคสนี้ก่อนส่งงาน

## 5. PHASE 1 — ตรวจ Flow ทีละหน้า (ทำทีละหน้า ห้ามเหมารวม)

ตรวจ **1 หน้า ต่อ 1 รอบ** ตามลำดับนี้ และแต่ละหน้าต้องตอบครบทุกช่องในตารางนี้ก่อนไปหน้าถัดไป

| ช่องที่ต้องตอบ | รายละเอียด |
|---|---|
| Trigger | ผู้ใช้กดอะไร → ยิง endpoint ไหน method อะไร |
| Payload | ส่ง field อะไรบ้าง ชนิดข้อมูลตรงกับคอลัมน์ DB ไหม |
| Validation ฝั่ง JS | เช็คอะไรก่อนส่ง |
| Validation ฝั่ง Go | เช็คซ้ำอะไร (ห้ามเชื่อฝั่ง JS อย่างเดียว) |
| Authorization | `mb_id` ใน URL ตรงกับ `mb_id` ใน JWT หรือไม่ — **ถ้าไม่เช็ค = ผู้ใช้ A แก้ข้อมูลผู้ใช้ B ได้** |
| DB Write | เขียนตารางไหนบ้าง เป็น transaction เดียวหรือไม่ |
| Response | คืนอะไร หน้าจออัปเดตยังไง (re-fetch หรือแก้ DOM ตรงๆ) |
| Error path | ถ้า API ล้ม / 401 / เน็ตหลุด หน้าจอทำอะไร |
| ผลตรวจ | ✅ ถูก / ⚠️ ต้องแก้ / ❌ ยังไม่ได้ทำ |

### ลำดับหน้าที่ต้องตรวจ

**หน้า 1 — ลงทะเบียน (DFD Process 3)**
เงื่อนไขผ่าน: 1 คำขอสมัคร ต้องเขียน **3 ตารางใน transaction เดียว** คือ `member_profile` → `member_body_stats` → `member_bmr_history` ถ้าตารางใดล้มต้อง rollback ทั้งหมด
*ปัจจุบันเขียนแค่ 2 ตารางแรก ทำให้ผู้ใช้ใหม่เข้า Dashboard แล้วเจอหน้าว่าง — นี่คือบั๊กหลัก*

**หน้า 2 — เข้าสู่ระบบ (DFD Process 1)**
ตรวจ: แยก endpoint admin/member จริงหรือไม่ · role ที่คืนมาตรงกับตารางที่ query หรือไม่ · `guardMember()` / `guardAdmin()` ทำงานก่อน paint จริงหรือไม่ · ถ้า member ยัด URL หน้า admin ตรงๆ เกิดอะไรขึ้น
*[ตัดสินใจแล้ว 2026-08-25: ห้ามซ้ำข้ามตาราง — ดู §7]*

**หน้า 3 — โปรไฟล์ / แก้ไขข้อมูลร่างกาย**
เงื่อนไขผ่าน: กด "บันทึก" แล้วต้อง insert `member_body_stats` **และ** คำนวณ + insert `member_bmr_history` ทันทีใน transaction เดียว
ตรวจเพิ่ม: ถ้าค่าน้ำหนัก/ส่วนสูงไม่เปลี่ยนเลย ควร insert แถวใหม่หรือไม่ (ปัจจุบัน insert ทุกครั้ง ทำให้ `mbs_id` 3 กับ 4 ค่าเหมือนกันเป๊ะ ต่างกัน 5 นาที)
ตรวจเพิ่ม: `profile.js:330` และ `profile.js:355` ยังเป็น `TODO` — เปลี่ยนรหัสผ่านและ logout **ยังไม่ได้เชื่อม API จริง**

**หน้า 4 — บันทึกอาหาร (DFD Process 5)**
ตรวจครบ CRUD: เพิ่ม / แก้ไข / ลบ / ดึงตามวันที่
เงื่อนไขผ่าน:
- ต้องแสดงจุดสี traffic light ทุกแถว และถ้า `fd_id` เป็น NULL ต้องมี fallback ที่ชัดเจน (เช่น จุดสีเทา + ข้อความ "ไม่ระบุประเภท") ห้ามเรนเดอร์ว่าง
- ห้ามบันทึกวันที่ในอนาคต
- แก้ไขแล้ว `dfd_updated_at` ต้องเปลี่ยน แต่ `dfd_created_at` ต้องไม่เปลี่ยน
- ลบแล้วต้องมี dialog ยืนยัน และ list ต้อง re-fetch ไม่ใช่ลบ DOM เฉยๆ

**หน้า 5 — บันทึกกิจกรรม (DFD Process 6)**
ตรวจครบ CRUD เหมือนหน้า 4
เงื่อนไขผ่าน: `dact_duration_min` ต้องเป็น **จำนวนเต็มหน่วยนาที** ตรงกันทั้ง input / JSON / Go struct / คอลัมน์ DB (ปัจจุบัน `Datasic.sql` เขียนเป็น `TIME` แต่ DB จริงเป็น `int` — ต้องเลือก `int` แล้วแก้เอกสาร)
ต้อง validate: > 0 และ ≤ 1440

**หน้า 6 — บันทึกการนอน (DFD Process 7)**
เงื่อนไขผ่าน:
- `dslp_total_hours` ต้องคำนวณฝั่ง Go จาก `end − start` เท่านั้น ห้ามรับค่าจาก client
- ต้องรองรับการนอนข้ามคืน (เข้านอน 23:00 ตื่น 07:00 = 8 ชม.)
- ต้อง reject ถ้า `end <= start` หรือชั่วโมงรวม > 24
- `dslp_eval_result` ระบบคำนวณ / `dslp_quality_score` ผู้ใช้เลือก — ห้ามปนกัน (ดู §2.6)
- ควรมี UNIQUE `(mb_id, dslp_date)` หรือระบุชัดว่า 1 วันบันทึกได้หลายครั้ง — ตัดสินใจแล้วเขียนลง spec

**หน้า 7 — Dashboard ผู้ใช้ (DFD Process 8)**
เงื่อนไขผ่าน:
- **ทุกตัวเลขต้องมาจาก API เท่านั้น** ปัจจุบัน `index.html` hardcode BMI 22.5, 1,520 / 2,150 / 1,800 kcal ไว้ใน HTML → ต้องเอาออกให้หมด
- `app.js` อ่านค่า BMI จาก `document.getElementById('bmiValue').innerText` ซึ่งเป็น anti-pattern → ต้องเปลี่ยนเป็นรับค่าเป็น argument จาก state ไม่ใช่อ่านย้อนกลับจาก DOM
- ต้องมี loading state และ empty state (ผู้ใช้ใหม่ที่ยังไม่มีข้อมูล)
- ดึง BMR ล่าสุดต้องใช้ `ORDER BY mbh_id DESC LIMIT 1` **ไม่ใช่** `ORDER BY mbh_record_date` เพราะวันเดียวกันมีได้หลายแถว (mb_id 6 มี 3 แถวในวันที่ 2026-08-24)
- **ตัดสินใจแล้วเขียนลง spec:** จะแสดง "พลังงานที่กิน (kcal)" หรือไม่ — ถ้าจะแสดง ต้องเพิ่มคอลัมน์แคลอรี่ ถ้าไม่ ต้องลบการ์ดนั้นออกจาก UI ห้ามปล่อยให้โชว์เลขปลอม (ดู §7)

**หน้า 8 — จัดการข้อมูลพื้นฐาน Admin (DFD Process 2)**
ตรวจ CRUD ทั้ง `food_category` และ `activity_master`
เงื่อนไขผ่าน:
